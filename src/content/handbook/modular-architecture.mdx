## Principle

Each component should own a narrow, explicit responsibility. A system becomes easier to change when no module silently claims the authority of its neighbors.

## When it matters

Use modular boundaries when a product joins UI state, durable records, synchronization, model-assisted work, or multiple runtimes that will evolve at different speeds.

## Reusable pattern

Name the authority for every durable concern, define the handoff between modules, and extend the existing boundary before introducing a new control layer. Prefer a small adapter over duplicated state.

## Failure mode

A new coordinator becomes the unofficial source of truth, repeats persistence logic, or reaches across layers directly. Changes then require synchronized edits in places that cannot be reasoned about independently.

## Practical checklist

- Name the source of truth for each durable record.
- Give each interface one accountable responsibility.
- Keep adapters explicit at runtime and storage boundaries.
- Test a change at the boundary where it belongs.
